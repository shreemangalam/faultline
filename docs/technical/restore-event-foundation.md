# Restore durable event foundation

Restore accepts durable recovery events through `POST /api/v1/events`, returns an existing event for an identical idempotent submission, and rejects a reused key with different business input. `GET /api/v1/events/{eventId}` returns persisted state, prerequisite IDs, lease details, and audit history; `GET /api/v1/events?status=ELIGIBLE` exposes the operational queue.

An event may name up to 20 prerequisite event IDs. Prerequisites must exist, be unique, and use the same correlation ID. If any prerequisite is not `COMPLETED`, the new event is persisted as `BLOCKED` with an audit entry; otherwise it is `ELIGIBLE`. Prerequisite membership is part of the idempotency fingerprint, so reusing a key with changed dependencies is rejected. A successful worker completion releases a blocked dependant only after every persisted prerequisite is `COMPLETED`.

A worker calls `POST /api/v1/worker/claims` with a worker ID, batch size, and lease duration. Restore selects due eligible events and expired `IN_PROGRESS` leases with a transactional `FOR UPDATE SKIP LOCKED` query, then persists `IN_PROGRESS`, the lease owner and expiry, an incremented attempt count, an attempt record, and an audit entry before returning work. This is at-least-once processing: a crashed worker’s lease becomes visible for another worker to reclaim. Reclaiming closes the abandoned attempt as `LEASE_EXPIRED` before creating the next numbered attempt. The lease-owning worker completes work through `POST /api/v1/worker/claims/{eventId}/complete`; a stale or different worker is rejected. The first two transient failures schedule 5s and 10s base delays plus a configurable inclusive 0–2 second jitter window. The third claimed failure becomes `EXHAUSTED` rather than retrying forever; the policy continues toward a 60s cap only if the attempt limit is extended. Event reads expose ordered attempt outcomes and timestamps. A lease owner can terminate non-retriable work as `FAILED_FINAL`; the attempt is recorded as `PERMANENT_FAILURE` without incrementing the target circuit. A configurable fixed-delay scheduler invokes the same bounded executor as the manual endpoint. It is opt-in so starting a developer process cannot deliver preserved work unexpectedly; batch failures are contained, and a process-local overlap guard complements cross-process database leases. Aggregate observability and repeatable load scenarios remain next.

Each target system has a persisted `CLOSED`, `OPEN`, or `HALF_OPEN` circuit visible at `GET /api/v1/circuit-breakers`. Three qualifying transient failures open the circuit for 30 seconds. Claims are suppressed during cooldown; after cooldown, a pessimistically locked circuit row permits one half-open probe. Probe success closes and resets the circuit, while probe failure reopens it for 60 seconds.

The local downstream simulator is controlled through `PUT /api/v1/simulator/targets/{targetSystem}` and accepts deliveries at `POST /api/v1/simulator/targets/{targetSystem}/deliveries`. It returns success, `503`, `429`, delayed success, or permanent validation failure on demand. Successful deliveries deduplicate on `Idempotency-Key` and expose request versus accepted counts. Simulator controls are intentionally ephemeral test-fixture state; recovery events, attempts, and circuit health remain durable PostgreSQL state.

Survey and Restore currently share the local PostgreSQL database for an easy Compose demo. Restore uses a separate Flyway history table and baselines at version `0` before applying its own migrations, which lets it migrate alongside Survey without treating Survey tables as its schema history.

Run the full local stack with `docker compose -f infra/compose.yaml up --build`; Restore health is at `http://localhost:8082/actuator/health`.
